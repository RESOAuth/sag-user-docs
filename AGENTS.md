# AGENTS.md

## What this repository is

The documentation site for SAG (Smart Access Gateway), an open-source,
stateless identity proxy by RESOAuth Ltd. This repository holds **only user
documentation**. The software lives at
[RESOAuth/smart-access-gateway](https://github.com/RESOAuth/smart-access-gateway).

Built with Docusaurus 3. Content is Markdown; the build exists for versioning,
search, and link checking.

## The two audiences, and why the site splits the way it does

Every page belongs to one of these. If you cannot tell which, the page is
probably two pages.

1. **Using the gateway RESOAuth® runs** (`docs/hosted/`). The reader has an
   application and wants sign-in working. They do not deploy anything and
   cannot change any environment variable. Never send them to a `SAG_*`
   variable as an instruction; mention one only to say what the operator
   controls.
2. **Deploying it yourself** (`docs/self-host/`, `docs/reference/`). The
   reader runs the software. Every switch is fair game.

## What does not belong here

This site is for getting people **using** SAG. It does not carry the reasoning
behind the software, and it does not duplicate what the code repository
already documents.

Limitations, architecture decision records, RFCs, and the post-quantum
discussion live in
[the SAG repository's `docs/`](https://github.com/RESOAuth/smart-access-gateway/tree/main/docs)
and are **linked to, never copied**. The site had a `background/` section
mirroring them once; it was removed precisely because two copies of a decision
record is one copy too many, and the one next to the code is the one that
stays correct.

So when a page needs to cite a decision, use an absolute GitHub URL:

```md
The reasoning is in
[ADR 0005](https://github.com/RESOAuth/smart-access-gateway/blob/main/docs/adr/0005-no-refresh-tokens.md).
```

The test for a new page: does it help somebody use or run SAG? If it explains
why something was decided, or what is proposed but not built, it belongs
upstream.

Deployment and configuration pages are copied here despite also existing
upstream, because running the software is the site's stated purpose. That is
the exception, and it is not a licence to widen it.

## Where things are

- `docs/` - the unreleased version, served at `/next`.
- `docs/_snippets/` - Markdown partials. Leading underscore, so Docusaurus
  does not turn them into pages. Import into `.mdx` only.
- `versioned_docs/version-X/`, `versioned_sidebars/`, `versions.json` -
  cut releases. Edit a file here only to correct that release.
- `docusaurus.config.ts` - reads `versions.json`, so the version number is
  never written out twice. Do not hard-code a release anywhere else.
- `sidebars.ts` - four sidebars, each `autogenerated` from one folder.
  Adding a page needs no edit here.

## Conventions to follow

- **Internal links are relative and keep the `.md`/`.mdx` extension**:
  `[Configuration](../reference/configuration.md)`. Docusaurus resolves these
  per version, so the reader stays in the version they are reading. An
  absolute path such as `/reference/configuration` silently drops them into
  the default version. This is the single easiest thing to get wrong here.
- **Link text is a title, never a filename.** `[Configuration](...)`, not
  `[configuration.md](...)`.
- **Links into the code repository are absolute GitHub URLs**, because the
  code is not in this repository. Use
  `https://github.com/RESOAuth/smart-access-gateway/blob/main/<path>`.
- **Every page carries frontmatter** with `sidebar_label`, `sidebar_position`,
  and a one-sentence `description`. The description is used for search results
  and link previews, so write it as a sentence.
- **Do not set `title:` in frontmatter** when the page has an H1. You get two
  headings. The H1 is the title.
- Prose style: British English, Oxford commas, hyphens instead of em-dashes,
  terse and direct. Aim at a twelve-year-old reading age for the sentences
  without simplifying the technical content, and do not reach for analogies to
  explain cryptography or protocol behaviour. Match the voice already in the
  files rather than introducing a different one.
- No personal names or identifying information: this is a public repository.
  Use "Jamie Taylor" as a placeholder, matching the code repository.
- Use and direct human operators to a `questions.md` in the root if anything needs clarifying.

## Keeping in step with the software

Pages under `self-host/` and `reference/` are copies of files in the SAG
repository's own `docs/`. They are copies rather than a live import because
this site is versioned per release and the code repository is not.

When porting a change across:

- Re-check the relative links. The folder layout here is not the layout there.
- `docs/hosted/` has no counterpart upstream. It is maintained only here, and
  a change to SAG's behaviour usually needs a matching edit in it.
- If SAG adds an environment variable, it belongs in
  `docs/reference/configuration.md` (or `relying-parties.md` /
  `upstreams.md` for per-client and per-upstream ones), matching where the
  code repository puts it.

Do not invent behaviour. If a page needs a fact about SAG that is not already
written down, read the source rather than guessing: `src/config.js` parses
every environment variable in one place, `src/router.js` holds the route
table, and `src/endpoints/` is one file per route.

## Versioning

Versions are full semver, `x.y.z`, matching SAG's own release numbers. The
current release is 0.1.0.

A **minor or major** release is a new cut:

```sh
npm run cut-version -- 0.2.0
```

Snapshots `docs/` into `versioned_docs/version-0.2.0/` and prepends it to
`versions.json`. The config reads that file, so 0.2.0 becomes the default,
0.1.0 starts serving an "unmaintained" banner on its own, and `docs/` goes
back to being the unreleased `/next`.

A **patch** release is not a new cut - it corrects the version that is
already out, so it edits that version's files in place instead of adding
another entry:

```sh
npm run bump-patch -- 0.1.1
```

This renames `versioned_docs/version-0.1.0/` and the matching file in
`versioned_sidebars/` to `0.1.1`, and rewrites the existing entry in
`versions.json` rather than growing the array. Make the actual content fix
inside `versioned_docs/version-0.1.1/` (before or after running it, either
order works), then commit the rename and the fix together.

Either way, nothing else needs editing except the `announcementBar` text, if
the release is worth announcing.

Cut or patch a version only when SAG does, and match its version number.

## Before calling anything done

```sh
npm run build      # fails on a broken internal link, so this is the link check
npm run typecheck
```

Both run in CI on every pull request. The build is not slow, so there is no
excuse for skipping it. A page that is not reachable from a sidebar, or that
links to a file that moved, will pass a casual read and fail here.
